01

Executive summary

This project automates representative storefront tasks on Amazon.com and create/read operations against the public Swagger Petstore sandbox. It keeps UI and API tests independently runnable and organizes browser behavior behind Page Objects.

What is demonstrated

Reliable locator strategy, web-first assertions, reusable page actions, typed API payloads, response and follow-up checks, test tagging, failure diagnostics, and a repeatable GitHub Actions workflow.

Safety boundary

The Amazon flow stops at the sign-in checkpoint. It does not submit credentials, payment information, or a real order. Petstore is used for API practice because Amazon does not provide a public sandbox API for this exercise.

Live-site limitation - transparent result reporting Amazon is a third-party storefront that may vary by inventory, delivery region, consent, or anti-automation response. A skipped UI test is not a pass. The latest local full-suite run recorded below had 3 API passes and 7 UI skips after Amazon returned its automated-session challenge.

Test design and project layout

03

Amazon UI scenarios

All seven scenarios use a fresh Playwright browser context. Shared cart state is not assumed, and the checkout case ends at the expected sign-in prompt.

Homepage availability

Open the configured storefront. Verify the Amazon page title, logo, and search input are visible.

Search relevance

Search for wireless mouse, wait for result listings, and require at least one result title matching the search phrase.

Brand filter

Search for the product and select the Logitech brand filter. Verify navigation reflects the filter action and results remain visible.

Product details

Open a listing and verify product title, price, customer rating, and primary image.

Add to cart

Record the initial cart count, add the product, and assert the displayed count increases by one.

Cart contents

Open the cart and check the selected product title, quantity of one, and a visible non-zero subtotal.

Checkout sign-in checkpoint

Proceed from the cart only until Amazon displays its sign-in prompt. No login or purchase is attempted.

UI skip conditions The homepage helper detects Amazon's "Click the button below to continue shopping" challenge and skips the UI case before scenario assertions run. This is unrelated to login. A product scenario can also skip when Amazon explicitly reports that the listing cannot ship to the active delivery location. Review skipped results as unexecuted tests, not successful validations.
04

Swagger Petstore API coverage

Base URL: https://petstore.swagger.io/v2. Requests accept JSON; POST requests send JSON payloads. Created records use generated identifiers to reduce collisions in the shared sandbox.

CaseRequest sequenceKey validations
Available petsGET /pet/findByStatus?status=availableHTTP 200; response is a non-empty array; each pet has available status, ID, name, and photo URL list; elapsed time under 2,000 ms.
Create and read petPOST /pet, then GET /pet/{id}HTTP 200; response preserves submitted ID, name, and status; follow-up GET returns the created pet details.
Create and read orderCreate a test pet, POST /store/order, then GET /store/order/{id}HTTP 200; returned pet ID and placed status match; quantity is a positive integer; follow-up GET returns the order fields.

The order case creates its referenced pet as setup, so its order payload refers to a real sandbox record. The public Petstore is shared and may be reset or respond variably.

05

Reliability and maintainability choices

Browser behavior

  • Uses Playwright web-first expectations rather than fixed sleeps.
  • Centralizes Amazon selectors and actions in Page Objects.
  • Uses stable IDs and semantic role/text locators where available.
  • Uses a bounded homepage check to distinguish storefront from a known challenge.
  • Does not bypass bot protection or automate purchase completion.

API behavior

  • Uses Playwright APIRequestContext, JSON headers, and typed payload interfaces.
  • Asserts status and response data, then verifies persisted create/read flows.
  • Disposes each request context after each test.
  • Uses unique runtime IDs to avoid fixed-ID conflicts in the shared service.
  • Keeps API tests independent of browser behavior.
Diagnostics on failure Playwright is configured for an HTML report, screenshots on failure, traces retained on failure, and failure video. CI uploads playwright-report/ and test-results/ even when a test step fails.
06

Run and reporting guide

Prerequisites: Node.js 20 or newer, npm, and network access to the public targets. From the project root:

npm install
Copy-Item config/.env.example config/.env
npm run install:browsers

npm run typecheck
npm test                 # complete UI and API suite
npm run test:ui          # Amazon UI only
npm run test:api         # Petstore API only
npm run test:smoke       # @smoke scenarios
npm run report           # open latest HTML report

GitHub Actions runs on pushes and pull requests targeting main, with a manual workflow_dispatch option. The workflow installs Chromium, typechecks, runs the full suite, and retains the report and test artifacts for 14 days.

Important about test status Playwright's skipped count means the test did not run its assertions. Amazon can challenge hosted CI traffic. For evaluation, use an approved test environment or an authorized run where Amazon serves the storefront; do not describe skipped UI tests as passes.

Suggested committee talk track

  1. Scope: “This suite tests seven guest shopping interactions on Amazon and three create/read API cases on Petstore. Checkout stops before sign-in or purchase.”
  2. Design: “Amazon locators and actions live in Page Objects; tests stay focused on scenario intent. The API tests use typed data and verify both create and read behavior.”
  3. Execution: “I can run UI and API suites independently or together. GitHub Actions installs the browser, typechecks the project, executes tests, and stores the report.”
  4. Evidence: “The API cases passed locally. The UI tests were skipped when Amazon served its challenge page, so I am reporting that as an environment restriction, not a test pass.”
  5. Safety: “The automation does not use account credentials or submit an order. To validate the full live storefront flow, we need an approved test setup that permits automation.”
“The suite demonstrates the automation architecture and assertions; the report also makes the limits of a live third-party storefront visible and auditable.”
